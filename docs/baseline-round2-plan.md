# Plan for round 2 of the classical baseline

**TL;DR:** Wave 1 freezes the yardstick (E00: linear-r1 alias, BEST_SPEC fingerprint, a frozen pre-round jar as the cost reference, a CPU-time bench and CPU-ms per move in the arena) and then lands, in disjoint files, two identical-tree speed packs (E01/E02, measured x1.75-2.2 nodes/s with an unchanged checksum), the race module with the sound S1 criterion (E03, now with a written soundness statement, lemma tests and an exhaustive adversary, in the tablebase module created right away; +66 to +77 Elo measured) and the refit of the linear weights on passed-filtered BEST self-play with an independent gate (E04; +88 to +105 measured against linear-r1). Wave 2 adds the tree-changing search gain (E06 futility at depth 1 and 2, +111/+113 cost-adjusted, now with win, move-limit and race-band exclusions and a win-in-1 test), bestGain after futility so the margins are tuned once (E07), racelin as a leaf value inside a score band that labels, value targets, aspiration and futility all recognise and ignore (E08), the rows>=1 CPU table (E09) and the self-play tool whose adjudication is accepted only with Clopper-Pearson bounds from fully played-out control games (E05); only the integration commit changes Strategies.BEST_SPEC. Wave 3 prepares stages 2 and 1 in parallel: teacher samples with root scores computed with fut, lmr and qs off (E10), classical input planes and residual priors (E11, owner decision), the GPU retrograde BFS (E12), the incremental evaluator (E13) and the quiescence re-test (E14). Strength is reported as two separately measured numbers: node-equal Elo against R2 (the parts race, refit and futility were each measured against their own baseline and are not additive) and equal-cost Elo from the integration match in which BEST plays R2 at 20000 x nps_new/nps_old nodes, so the speed packs' share (estimated at about +100 from the nodes-Elo spacing) is measured rather than derived. Training cost is likewise two numbers: the classical teacher cost per sample (measured; 2 to 3 times cheaper after the speed packs) and the share of network self-play plies that race play and adjudication save (18.4% and 8-16% on BEST games; a lower bound is measured on weak-player games because early generations pass later or never), and throughout only S1 may label race positions.

This plan was produced on 2026-11-07 by three surveyors (speed, classical knowledge, search and training use) who measured on copies of the repository, merged by a planner and revised after an independent critic attacked it. Numbers marked *measured* come from the surveyors' prototypes; all others are estimates. Nothing in this plan is implemented yet. Each experiment is to be run by an independent agent in its own worktree and re-measured by an independent verifier, as in round 1.

## Yardstick

Reference R2 = `ab:eval=linear-r1,pvs=1,killers=1,history=1,lmr=2,asp=1,ttrep=1,mate=1,partial=1,nodes=20000`: today's BEST_SPEC with its weights frozen under the registry name linear-r1 (E00), constructible in every later build, its tree pinned by BestSpecFingerprintTest (move, score, depth, nodes over 64 sampled positions plus one 1000-node and one 5000-node self-play game). Ladder: R0 = ab:eval=distance,nodes=20000 (sanity only, saturated at 198/200); R1 = R2 at 5000 nodes; R2; R3 = R2 at 80000 nodes. Measured spacing around R2: 28k nodes +69 +- 32, 36k +110 +- 39, 40k +104 +- 32; at 200 pairs the interval is about +-32 Elo, at 300 about +-26, at 500 about +-20, at 2000 about +-10. COST REFERENCE (critique 'round total', resolved): the pre-round build is frozen as a jar outside git (E00; commit id and SHA-256 recorded in docs/search-and-evaluation.md) and nps_old is measured from it with the same Bench tool, so an equal-time claim against R2 is possible: R2 at 20000 nodes on the new build plays the same tree as the old build (fingerprint), and BEST at 20000 x nps_new/nps_old nodes has the old player's time budget. NPS RATIOS (critique 'yardstick', resolved): never taken from an arena report under shared load; the Bench tool (E00) runs single-threaded, A and B interleaved three times (A,B,A,B,A,B; across builds via a shell script that alternates classpaths), over the 64 fingerprint positions plus 2 full games, measures thread CPU time with ThreadMXBean.getCurrentThreadCpuTime, logs the load average before and after and refuses to report when the 1-minute load exceeds the core count; the ratio is fixed before the arena run and quoted in it. Arena prints CPU-ms per move per player (ThreadMXBean in GameRunner) beside wall time; cost criteria such as E03's 'not slower' use the CPU column. Protocol for every strength claim: paired games with colours swapped, 4 random opening plies, --threads 4, node limits (load-independent); when the candidate's cost per node differs, run equal nodes first and then candidate nodes = 20000 x nps_candidate / nps_opponent from the Bench ratio; authors tune on seeds 31 and 32 only and report seeds 33 and 34 (300 pairs each); the verifier re-measures on seeds 41 and 42 (300 pairs; 500 when the claimed gain is below +50 Elo), reads the diff for unfair advantages (information the opponent cannot have, changed rules, changed opening generation, race-band scores leaking into labels) and reruns the full build including nn (`devenv shell -- ./gradlew --no-build-cache build`, all modules). Acceptance: lower 95% bound > 0 on both verifier seeds against the current BEST_SPEC; the result against R2 is reported as well. Identical-tree changes need no arena: both fingerprints unchanged plus the Bench ratio. Only the integration commit after each wave changes Strategies.BEST_SPEC. INTEGRATION (critique 'integration', resolved): the new BEST_SPEC plays R2 and the previous BEST_SPEC, 500 pairs each on seed 43, at equal nodes AND at equal cost (BEST at 20000 x nps_new/nps_old vs R2 at 20000); the summary reports both numbers separately and labels the difference as the speed share. The parts were measured against different baselines and are not additive, so the sum is a rough expectation only: investigate an interaction only when the equal-nodes integration result falls below the sum by more than the combined interval sqrt(sum of the parts' squared half-widths + the integration run's squared half-width); otherwise report the shortfall. Re-base rule: when BEST scores above 0.80 against R2 (about +240 Elo) the arena saturates again; freeze the new BEST as R2' (new registry alias and fingerprint) and keep R2 in the ladder. LABEL POLICY (critique E08 blocker, resolved, applies everywhere): scores with |score| >= RACE_BASE (the racelin band, E08) are never used as labels or value targets; only S1 (E03) may label passed positions; every error claim for an adjudication rule states the number of firings, the number of errors found by playing the game to the end, and the one-sided 95% Clopper-Pearson upper bound (0 of n: about 3.0/n; 1 of n: about 4.74/n; 2 of n: about 6.3/n), so '< 0.5%' needs 0 of >= 600, 1 of >= 950 or 2 of >= 1260 firings. Training-cost yardsticks, reported with every merged change, in two groups: classical (measured): self-play games/s per core at 1000 nodes (10.1 before the round, 16.9 with the speed prototypes), ms per teacher sample with depth-3 root scores (12 ms before); network self-play (estimate, measured as shares on games): share of plies saved by adjudication at 0 label errors (8.0% with S1 on BEST games), share of plies played classically (18.4% on BEST games), both ALSO measured on games of ab:eval=distance,nodes=1000 as the lower bound for early network generations, and wrong labels among fully played-out adjudicated games (must stay 0 for S1 and below the Clopper-Pearson rule above overall). Optional SPRT (H0 = 0, H1 = +20 Elo, alpha = beta = 0.05, on pair scores) is for authors' tuning loops; verifier runs stay fixed-size for comparability with round 1.

### E01: Search speed pack: lazy selection in move ordering, static LMR table (tree identical)

- **Wave:** 1; **effort:** small; **depends on:** E00
- **Hypothesis:** AlphaBeta.order (lines 459-474) selection-sorts all 40-65 moves at every interior node, but interior nodes search only about 5 moves before a cutoff (85-92% of interior nodes are at depth 1); doing selection step i only when move i is needed gives the identical order with 4-6x less ordering work, which is 27-34% of node time.
- **Implementation:** Critique (E02 minor): resolved by depending on E00 (fingerprint of the linear tree exists before this merges) and by running the full build including nn. search/src/main/java/sternhalma/search/AlphaBeta.java only. order() fills orderKeys[height] and returns without sorting; a static pick(moves, keys, i, count) performs one selection step with the original strict '>' comparison and swaps both arrays (ties must come out in the same order). Call pick(...,0,...) right after order() in negamax and searchRoot (keeps `bestMove = moves[0]` and the partial-iteration logic correct), and pick(...,i,...) at the top of each move loop. LMR: replace the per-instance lmrTable (78k Math.log calls, 1.23 ms per player) by a static table per lmr mode computed once. Tests: new search/src/test/java/sternhalma/search/MoveOrderingTest.java (pick() over random keys with ties yields the same prefix as the full selection sort for every i); DefaultBehaviourTest and E00's BestSpecFingerprintTest unchanged; existing AlphaBetaTest, SearchOptionsTest and RegisteredStrategiesContractTest green; `./gradlew --no-build-cache build` over all modules.
- **Measurement:** No arena needed. Acceptance: both fingerprint tests unchanged (identical tree); Bench ratio new/old >= 1.30 (median of 3 interleaved single-threaded repetitions, thread CPU time, load logged, per E00). Both surveyors measured x1.39-1.44 and x1.3-1.4 (ablation: 1.53M vs 1.14M and 1.46M vs 1.00M nodes/s, wall time under load; the CPU-time figure may differ). Failure: fingerprint change, or ratio < 1.20.
- **Expected:** x1.3-1.45 nodes/s. ### E03: Race module in a new tablebase module: solitaire generator, rows>=2 table, race-play hook (race=1) and sound S1 adjudication with a written soundness statement

- **Wave:** 1; **effort:** medium; **depends on:** none
- **Hypothesis:** After the armies pass (999 of 1000 BEST games, mean ply 76, 18.4% of all plies), the game is two solitaire problems; BEST's depth-4/5 search with the linear evaluation wastes race tempi (longer than optimal in 228 of 919 games, 10 forced races not converted in 999) and loses close races, while an exact or near-exact solitaire move is stronger and cheaper. A frontier-guarded race criterion (S1) ends such games with a label that cannot be wrong, and its soundness follows from a lemma about row advance that can be tested directly.
- **Implementation:** Critique (E03 major, 'missing' items 1 and 8, E09/E08 minor): resolved as follows. (1) Soundness statement in RaceAdjudication's javadoc, with preconditions that the code checks and otherwise returns 'not applicable': rules.players() == 2, blockingStates == NONE, no pass move (the engine has none; count==0 ends the game), leaveGoal either value (the beam respects FORBIDDEN), repetition rule any (plan states are asserted distinct, so W's configuration never repeats), and the row axis property (every step direction changes the row by -1, 0 or +1, a jump by -2, 0 or +2). Statement: let F be Lo's front row, s the number of Lo moves made; if all W pieces stand on rows >= F+s+3 before Lo's move s+1 and Lo's front is <= F+s, then Lo's front after the move is <= F+s+1 (no hurdle exists on rows F+s+1 and F+s+2, and a jump landing needs a hurdle one row short of it); W's plan landing cells at W's move t lie on rows >= F+k+1 with k Lo moves played, so Lo never occupies them; W's chains use only W pieces as hurdles; in a passed position neither goal can hold an opponent piece (fewer than 10 cells lie behind a goal's front row), so Definition 1 and Definition 2 cannot shorten Lo's path or forbid a W plan move; the Lo bound (per piece 0 on target, 1 if same (q mod 2, r mod 2) class or adjacent, else 2, summed over an assignment) is admissible because each move moves one piece, a jump keeps the class and a step ends the move; with pW = 2U-1 (W to move) or 2U, pLo = 2LB or 2LB-1, the test pW < pLo and ply+pW <= moveLimit respects move parity and the limit. (2) The surveyor's `checkA=false` fast path (Race.java:90) and the `lbMode==1` table-count bound are NOT ported; the guarded method with the parity-assignment bound is the only public entry point. (3) Tests of the lemma and of the whole: GeometryRowAxisTest (for both players' orientations, every neighbour direction changes the row by at most 1 and every jump by at most 2, exhaustively over all allowed cells); FrontAdvanceLemmaTest (>= 1M random positions with W pieces on rows >= F+3 and Lo's front at F, every legal Lo move enumerated, assert new front <= F+1; also with W pieces placed as adversarially as the precondition allows, that is exactly on rows F+3 and F+4); LowerBoundAdmissibilityTest (LB <= exact unrestricted solitaire distance on 10,000 sampled Lo configurations solved by IDA*, and LB <= table count for all 13,123,110 rows>=2 states, a necessary condition); the replay test asserts the front-advance bound after every Lo move; and ExhaustiveAdversaryTest: from the first-S1 position of >= 200 sampled games, Lo plays EVERY legal move at every Lo ply with a transposition set on Lo's configuration, W plays its plan, for every position whose plan has <= 4 Lo moves (the typical case: 7.5 plies saved per game means about 3-4 Lo moves), and for longer plans the exhaustive one-ply invariant check (front bound, W's next plan move legal, no Lo win) at every node of four full lines (BEST, the chaser, a random Lo, a front-maximising Lo); every leaf must be a W win on or before the predicted ply and no line may contain a Lo win or an illegal W move. (4) Module: E03 creates the `tablebase` module right away (settings.gradle.kts +1 line, tablebase/build.gradle.kts depending on :engine, search/build.gradle.kts gains `implementation(project(":tablebase"))`), with Ranking, RetrogradeBuilder, TableFile (header with format version, rules hash, k, cell list, state count, SHA-256 of the body) and RaceTable for rows>=2 (28 allowed cells, 13,123,110 states, byte entries, 12.5 MB; built on first use in about 16 s on 2 threads and cached under -Dsternhalma.tablebase.dir or build/tablebase/, lookup 0.8-1.5 us); search code reaches it only through the interface `sternhalma.tablebase.RaceCounts { int count(int[] ownCells); boolean covers(int[] ownCells); }` so E08/E09 need no API change. ## What the classical engine takes over from the network

- Legal moves and the policy mask: Position.generate (made cheaper by E02) supplies the legal (from, to) set for every sample, so the softmax runs over legal moves only and the network never learns legality (already in network.md; E02 makes the mask 0.7-0.9 us).
- Canonical orientation and the left-right mirror: Orientation and Geometry.mirror remove the rotations from the input and double the two-player data (already proposed in training.md; the opening sampler of E05 canonicalises by the mirror for statistics).
- Race endgames are played, not learned: after the armies pass (18.4% of all plies in BEST games; less in weak-player games, measured by E03/E05 as a lower bound), E03's race move (table-optimal, else beam) plays the position with no search and no network call; MCTS leaves in passed positions take the exact race value (E08) instead of the value head, so the value head models contact positions only.
- Race arithmetic and move counting are exact inputs or targets, never value labels: table counts (E03 rows>=2, E09 rows>=1, E12 rows>=0) give moves-left per side at about 1 us; they serve as a broadcast input scalar, as policy targets (table-optimal move sets) and as an auxiliary moves-left target; the conversion rule (a <= b and 2a-1 <= L) replaces any learned race judgement inside the search, while value labels of passed positions come only from S1 or the game result (band rule of E08, enforced in E05 and E10).
- Game adjudication with a stated error bound: S1 (E03) ends 8.0% of BEST plies with labels backed by a written soundness statement, lemma tests and an exhaustive adversary; the search-score margin of 500 (E05) ends another 7-10% with an error bound from fully played-out control games (Clopper-Pearson, accepted only below 0.5%); the control set is re-run for every network generation; the network never sees the late, decided plies and still gets exact value targets for the positions before the cut.
- Distance geometry: the single-agent distance table per cell (stage 2) becomes an input plane (E11, owner decision), so the network does not have to discover the goal geometry and the allowed-cell shape from occupancy planes.
- Jump connectivity: one-move reachability (legal landing cells of both sides) and bestGain (E07) are computed by the move generator and offered as planes or scalars, so the network does not have to learn long-range jump chains with a receptive field of about 9 cells.
- A sensible first policy and value: BEST_SPEC (new) as the generation-0 teacher (E10): softmax over full-window depth-3 root scores computed with fut, lmr and qs off (NLL 2.12 nats vs 3.92 uniform, a within-family proxy) as policy target and a blend of the game result with sigmoid(score/75) as value target (ORDINARY and MATE scores only); later generations keep a decaying share of teacher data.
- Priors inside MCTS (E11): beta x distance gain as the policy logit base (NLL 2.95 at table-lookup cost) and the linear evaluation as the value base, so the network learns corrections (blocks, bridges) and an untrained network already plays at the classical level.
- Openings: diversity comes from 4-10 random or classical-softmax plies (E05) at under 0.1% of self-play time; no opening book is built, because the measured upper bound of opening knowledge under random openings was +7 +- 32 Elo and a 1500-game book covers only 12-21% of arena openings.
- Gating and yardstick: the frozen reference linear-r1 (R2), the frozen pre-round jar (nps_old) and the ladder (E00) measure every network generation against a fixed classical opponent at equal CPU time (Bench), which catches self-play drift that a parent-only gate misses.
- Speed for all of the above: E01 and E02 (x1.75-2.2 nodes/s, tree identical) and E13 make every classical service, teacher sample, adjudication search and legal mask cheaper; the surveyors measured 10.1 -> 16.9 self-play games/s per thread at 1000 nodes with the prototypes. This lowers the classical teacher cost per sample; network self-play cost is lowered only by the race and adjudication shares, which are reported separately.

## Dropped ideas

When blockingStates=ILLEGAL or players=3, refuse to adjudicate.
- **[blocker] E08:** racelin returns +-5000 +- 200*diff from the unguarded race arithmetic using region tables, which are upper bounds. Through E05's layer 2 (|search score| >= 500 on 2 own moves) these values become game labels. Through E10 (sigmoid(score/75)) and E04/E05 layer 3 (sigmoid(eval/100)) they become value targets. The plan says the unguarded arithmetic must 'never' produce labels, but nothing stops this leak once racelin is in BEST_SPEC. The values also break E06: futility assumes the evaluation moves by at most about 30 per gained step plus a margin, but racelin jumps by 5000 when a move enters the table region. Only E07 re-probes DeltaProbe; E08 does not.
  *Proposed fix:* Make Adjudication layer 2, and every value target, ignore scores of 1000 or more that come from RaceEvaluator. One way: a flag in SearchResult, or a separate score band checked against a constant. Allow only S1 to label passed positions. Disable futility at nodes where RaceEvaluator could return a race value (passed, or both sides within one move of the region), or rerun DeltaProbe with racelin. Add E08 to E06's re-probe list. Measure E08 with fut on if E06 has merged by then.
- **[major] E06:** Futility can prune an immediate win, or a move that stops the opponent's win. Moves are sorted by distance gain, and the loop breaks at the first move whose bound is <= alpha. A goal-completing move with a small gain (often a one-step entry, gain 1) can sit behind that cut. The child's terminalScore is then never reached. The guard 'never when |alpha| >= MATE_BOUND' does not help, because alpha is an ordinary score while the win in 1 exists.
  *Proposed fix:* Skip futility at a node when goalOccupied[mover] >= CORNER_SIZE-1 or goalOccupied[opponent] >= CORNER_SIZE-1. Also exclude a move whose 'to' cell is in the mover's goal while that goal holds 9 pieces. Add a unit test: a position with a win in 1 whose winning move has gain 1, searched with fut=1, must return a mate score.
- **[major] E01/E02 (round total):** The protocol cannot measure the main speed claim (+100 Elo, and the round total of +250 to +350 at equal time). Every arena run uses node limits, and R2 (linear-r1) runs on the same faster code, so a speed gain scores exactly 0 against R2. The cost-adjusted rule compares two specs on the same build and never against the old cost. The round total therefore mixes measured node-equal gains with unmeasured speed estimates.
  *Proposed fix:* Keep a frozen jar of the pre-round build as the R2 cost reference. Measure nps_old/nps_new single-threaded and interleaved on an idle machine. Run the integration match with BEST at 20000 x nps_new/nps_old nodes against R2 at 20000 nodes. Report node-equal Elo and equal-cost Elo separately in the summary, and label the speed share as derived from the nps ratio.
- **[major] Yardstick:** The cost-adjusted runs take both nodes/s values 'from the same report'. Those arena runs use --threads 4 while other agents load the machine, so the nps ratio carries the load noise that node limits were meant to remove. The ratio also depends on the game phase: race plies are cheap, and race=1 searches no nodes at all. The E03 criterion 'time per move not higher' is wall-clock time under shared load.
  *Proposed fix:* Measure the nps ratio separately: 3 interleaved single-threaded repetitions over the 64 fingerprint positions plus 2 full games, with the load average logged, using thread CPU time (ThreadMXBean.getCurrentThreadCpuTime) rather than nanoTime. Fix that ratio before the arena run. Report CPU-ms per move in Arena instead of wall time.
- **[major] E05:** The error bounds are not supported by the sample size. 0 wrong out of 398 gives a 95% upper bound of about 0.75% (rule of three), above the 0.5% acceptance limit. A 10% control set of 1000 games has about 100 games, so 0 errors bounds the error rate only at about 3% to 7%. Layer-2 labels are also checked against BEST vs BEST play-outs. That is self-consistency, not correctness, and it fails once the network plays differently. 'Interval includes 0' for tt=16 accepts any small loss.
  *Proposed fix:* For the acceptance run, play every adjudicated game to the end offline, not only 10%. Require at least 600 layer-2 firings with 0 or 1 errors before claiming < 0.5%, and report the Clopper-Pearson bound. For tt=16 use a non-inferiority test: lower bound > -15 Elo at 500 pairs. Re-validate layer 2 against the current network player for every network generation.
- **[major] E04:** Overfitting and circularity: the weights are fitted on positions that the linear-r1 engine reaches and then gated only against linear-r1 at equal nodes. The data come from BEST without race=1, although E03 merges in the same wave and BEST is expected to stop searching passed positions. The fit then spends capacity on race positions where the evaluation will no longer be used. Repeated texel rounds gated only against the previous self are prone to drift.
  *Proposed fix:* Drop passed positions from the fit, or generate the data after E03 merges with race=1 on. Gate each texel round also against an engine that does not share the linear evaluation: stage4 at equal cost and R3 (80000 nodes). Accept only if the result against these does not fall by more than its interval. Cap the loop at 2 rounds in this round.
- **[major] E07:** Hidden dependency and merge conflict. E07's measurement spec includes '+ race=1 + fut' and re-tunes E06's margins, but dependsOn lists only E02 and E04. E06 and E07 both rewrite Strategies.BEST_SPEC in the same wave. E07 refits on E04's game files, which were played by the R1-weight engine without race play or futility, so the training distribution is already stale.
  *Proposed fix:* Make E07 depend on E06, or measure both with and without fut and let the integration step own the BEST_SPEC string. Only the integration commit may change BEST_SPEC. Regenerate the refit games with the wave-1 BEST, which is cheap at about 15 minutes.
- **[minor] E09/E08:** E09 moves RaceTable into a new tablebase module in the same wave in which E08's RaceEvaluator (search module) reads RaceTable. search then needs a dependency on :tablebase, which E08 does not expect. E09 also claims 'byte-identical' to E03's table, but E09 adds a header with a SHA-256 checksum, so only the bodies can be identical.
  *Proposed fix:* Fix the RaceTable API, the package and the module dependency (search -> tablebase) at the end of wave 1. Let E08 code against an interface. State that the check compares table bodies after the header.
- **[minor] E10:** 'Exact depth-3 root scores' are not exact once E06 is merged (futility at depth 1 and 2) and with LMR from depth 3. The NLL yardstick compares against the 100k-node move of the same engine, which is circular. The saving '36 vs 3-4 core-hours' compares teacher samples with MCTS samples. These are not the same product, and 128 ms per MCTS move is an estimate.
  *Proposed fix:* Compute rootScores with fut off, lmr off and a full window, and record the options in the sample flags. Label the core-hour comparison as an estimate. Make the measured gain the stage-2 result (pre-trained network vs randomly initialised network at equal core-hours).
- **[major] Summary (training savings):** 'Self-play data about 2 to 3 times cheaper per sample' holds only for classical self-play (games/s at 1000 nodes). In network self-play, network inference dominates the cost. The classical speed packs do not reduce it. Only adjudication (8% to 16% of plies, measured on BEST-quality games) and race plies (18.4%, measured on BEST games) reduce it. Early network generations reach the passed state later or never, so both shares will be smaller there.
  *Proposed fix:* Report two numbers: classical teacher cost per sample (measured) and the expected share of network self-play plies saved (estimate). Measure the second on games of a weak player (for example ab:eval=distance at 1000 nodes or a random-init MCTS) as a lower bound.
- **[minor] Yardstick (integration):** The integration rule 'gain more than 50 Elo below the sum of the parts' fires on noise. Four parts with an interval of about +-32 each give a summed interval of about +-64. The 500-pair integration match adds +-20. Elo measured against different baselines is also not additive.
  *Proposed fix:* Investigate only when the measured gain falls below the sum by more than the combined interval (sqrt of the sum of squared half-widths, plus that of the integration run). Otherwise report the shortfall.
- **[minor] E02:** The DefaultBehaviourTest is run with ab:eval=distance only (DefaultBehaviourTest.java:46-47). The 'unchanged' check therefore says nothing about LinearEvaluator, and for E02's evaluator part only E00's fingerprint and the equivalence test protect it. E00 must merge before E02, which the plan does not enforce (E02 dependsOn is empty). E02 also lists only engine and search tests, but Position is used beyond them, and the piece lists change Position.copy and put, which the nn encoder may call.
  *Proposed fix:* Add E00 to dependsOn of E01, E02 and E13. Run ./gradlew --no-build-cache build over all modules (including nn), not only the engine and search tests.

**Missing from the draft, according to the critic:**

- A formal soundness statement of S1, with its preconditions (two players, blockingStates=NONE, no passing, row axis), checked by an exhaustive adversary on sampled positions instead of the chaser.
- A rule that only S1 may produce labels or value targets from race positions; today E08's racelin scores can leak in through E05 layer 2, E05 layer 3 and E10.
- A frozen pre-round build (jar) as the cost reference, so that equal-time gains against R2 can be measured at all.
- nps ratios measured from thread CPU time on an idle machine, separate from arena runs under shared load.
- A win/blocking exclusion for futility (goalOccupied >= 9) and a unit test for a win in 1.
- An independent opponent family (stage4, R3) in the gate for weight refits, to detect self-play overfitting.
- Clopper-Pearson bounds and minimum firing counts for every adjudication error claim.
- Three-player handling: every race and adjudication component must refuse to run when players=3, with a test.

### E02: accepted although one sub-criterion was missed

The plan asked for a generator microbenchmark of at least 1.25 x. The verifier measured 1.20 to 1.23 x and marked the experiment as not confirmed. The experiment was merged all the same. Reason: the plan's purpose for that criterion is speed at an unchanged result, and the primary measurement meets it with a margin: 1.26 x on top of E01 against the required 1.12 x, with identical values and trees.

### E03: the acceptance wording about play-outs was changed

The plan required that the number of S1 firings whose game, played to the end by BEST, ends differently from the prediction must be 0. Measured: 6 of 997 (author) and 6 of 998 (verifier, other seed), one-sided 95% upper bound about 1.2%. All six are one-tempo races in which BEST at 20,000 nodes failed to convert a won race. For each of them the verifier showed that the predicted winner has a forced win (the plan played against the actual loser moves wins on time, and a full-width attack from the position finds no loser win).

**Amended criterion:** S1 is correct if no reply of the loser defeats the verdict (full-width attack on every verdict, and the plan played against the recorded loser moves). Disagreement between a verdict and the result of a game played by an imperfect player is not a label error: the verdict is the value of the position. About 0.6% of the games of the strongest engine therefore have a label that differs from the played result, intentionally.

Consequence for training data: S1 labels are game values and must not be replaced by the result of the self-play game.

### E04: delivered as `linear-r2`, not as a replacement of `linear`

The plan said to replace the weights of `eval=linear`. The author added the frozen set `LinearWeights.ROUND2` under the evaluator name `linear-r2` and left `linear` and `linear-r1` unchanged, which keeps the fingerprint and the yardstick intact. `Strategies.BEST_SPEC` still uses `linear`. The switch to `linear-r2` and the addition of `race=1` belong to the integration commit at the end of wave 2.

The second texel round used games without `race=1`, because E03 was not available to the author. The plan wanted games with race play for round 2. This is to be repeated at integration.

### E09: optional table in the cache, selected by a key, author seeds

The plan said "RaceTable loads the largest table found" and "a Gradle task writes data/tablebase/rows1.bin". Delivered instead (owner decisions): the rows ≥ 1 table (254,187,064 bytes) is never committed, not even through Git LFS; `:tablebase:buildTable -Prows=1` and `RaceTable.rows1()` build it on demand into `tablebase/build/tables/` (or `-Dsternhalma.tablebase.dir`) and check it against the constant `RaceTable.ROWS1_SHA256`; the rows ≥ 2 table remains the default of race play, and only the new spec key `racerows=1` uses the extended table, so existing specs play exactly as before and no result depends on what a machine has cached. Tests that need the table skip with a message when it is absent.

The plan's Elo measurement ("500 pairs, seed 41") used a verifier seed; the author measured on the report seeds 33 and 34 (300 pairs each) and the data-set seed 1005 for the coverage replays, leaving 41 and 42 to the verifier. Measured: +5.8 ± 5.0 and +2.3 ± 3.2 Elo at equal nodes and equal cost (the expected "0 to +15"); exact table moves in 88.7 % instead of 68.0 % of the race plies (the surveyor's 87 % confirmed); build 305.6 s on 4 threads (the plan's failure limit was 10 minutes), 113.1 s on 8. The plan's "1.03 % of rows ≥ 2 states are shorter in rows ≥ 1" is 0.08 % (10,558 of 13,123,110, each by exactly one move) on the committed tables. The table is validated exhaustively (every entry layer-consistent with the engine's moves), which proves it exact; the plan's "sampled forward IDA*" became a sampled forward BFS. The test JVM heap is raised to 2 GB in the convention plugin for the 254 MB array.

### Operations

The race table (about 12.5 MB) is stored with Git LFS. A table build without the LFS file takes 12 s on an idle machine and 33 to 58 s under load, not the 16 s that the plan assumed. Since E09 the builder needs roughly half the CPU time (merge-based ranks, no sort; 9.5 s on 4 threads under load against 11.9 s on 8 threads before, both on the shared machine), and the rows ≥ 2 table is reproduced byte for byte.
