### Is the diagnosis confirmed?
The diagnosis (cpp/README.md, 'x86 code generation of the SIMD path'): bounds checks inside the inner loop of the hardened build, and at 16 lanes a stack round trip
for every vector load, made the C++ path slow. The change removed both in one commit (the assembler loop has 18 instructions, 8 fma, no stack operand).
  - Hardened build: simd 16 lanes SMALL 1153.7 -> 8387.7 (7.27x), LARGE 203.8 -> 1197.4 (5.88x); simd 8 lanes SMALL 1939.3 -> 5139.9 (2.65x), LARGE 348.9 -> 818.8 (2.35x).
  - Cost of the checks (unchecked over hardened, batch 256, table checks_cost): run 1 SMALL 8 lanes 2.38x, run 2 1.002x; run 2, all four CPU programs and both presets: 0.971 to 1.006.
    The hardened build is now as fast as the unchecked one (within 3 %; below 5 % no statement). That the checks stood in the way is therefore confirmed: with them out of the
    loop the difference is gone.
  - 16 lanes against 8 lanes (hardened, SMALL / LARGE): run 1 0.59 / 0.58 (16 slower), run 2 1.63 / 1.46 (16 faster). The order has turned, as the stack-round-trip reading predicts.
  - Confirmed: the poor C++ numbers of run 1 were bad code from the bounds checks and the stack round trips, not a property of C++. Not separable from the data: how much each of
    the two causes contributed (they changed together), and the stall of the store-to-load forwarding itself was never measured. Results are unchanged: nn_check reports the same
    error fractions for every impl, preset and lane count as in run 1 (compared below), and the offline check of the commit found 12 equal digests of old and new code.
