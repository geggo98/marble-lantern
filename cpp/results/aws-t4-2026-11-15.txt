### The CPU rows are the uncomfortable ones
  - The comparison row (C++ 16 lanes against Java's 16 lanes) is SLOWER than Java Vector in the hardened C++ build: adjacent pairs 0.145 to 0.305, blocks 0.197 to 0.228
    (C++ over Java; SMALL batch 256: C++ 1153.7 against Java 5866.2 evals/s in the blocks), so C++ needs 3 to 7 times as long. The 8-lane row is faster than the
    16-lane row (SMALL batch 256: 1939.3, hardened) but still behind Java Vector.
  - The checks cost a lot here, unlike on the Mac: the unchecked 8-lane build reaches 4613.6 evals/s at SMALL batch 256 against 1939.3 hardened (table checks_cost, one run
    each; 2.3 times). The 16-lane build is much less affected (7 to 8 % for simd, none for simd-nofma). The cause was not investigated. The hardened build adds _GLIBCXX_ASSERTIONS; a bounds
    check that stops g++ 12 from vectorising or hoisting is a hypothesis, not a finding. The main rows of the plan use the hardened build, so they are booked as they are.
  - The CPU anchors move in steps, in both languages, while the GPU anchors do not. C++ simd (16 lanes), SMALL / LARGE: start 1153.6 / 203.7 then 760.7 / 132.2, end 1151.9 / 203.0 then 760.0 / 132.1;
    so the second C++ run of each pair block is about 34 % slower, at the start and at the end. Java Vector SMALL: 5056.2 / 3779.1 / 3779.4 / 3733.2.
    The C++ and Java blocks of the benchmark proper show no step inside the block (batches agree within 1 %), but they sit at one level: C++ at the fast level (round 1 of the
    anchors), Java Vector SMALL at 5,050 to 5,920 (the level of the first start anchor, not of the three later ones). The cause is not known (a noisy neighbour on the
    shared host or the clock behaviour of the CPU under AVX-512 load are plausible; neither is proven). By the rule the CPU rows stay unsettled, and no CPU ratio is
    more than indicative. Which level is the 'true' one cannot be told from n = 1.
